# 실시간 GEO 추천 시스템: 엔드투엔드 아키텍처 및 구현 가이드 (v2.5)

본 문서는 실시간 에지 컴퓨팅 기술과 비동기 오프라인 LLM 정밀 분석 파이프라인을 융합한 생성 엔진 최적화(GEO) 추천 시스템의 전체 아키텍처 구조 설계와 인프라 구축, 그리고 코어 워커 코드 구현 방안을 단일 명세로 정의합니다.

---

## 1. 아키텍처 구조설계서 (Architecture Specification)

### 1.1 아키텍처 개요 (Architecture Overview)
[cite_start]본 시스템은 Edge 환경에서 사용자 요청을 실시간으로 가로채어 본문의 시각적·기능적 노이즈를 제거하고 [cite: 4, 66][cite_start], 검색형 AI 엔진(SearchGPT, Perplexity 등) 친화적인 구조화 데이터(JSON-LD, Meta Tags)를 동적으로 합성·주입하는 것을 목표로 합니다[cite: 4]. [cite_start]시스템의 고가용성과 초저지연 성능을 달성하기 위해 계층 구조를 완전히 분리(Decoupled)하여 운영합니다[cite: 44, 81].

* [cite_start]**Hot Path (실시간 처리 영역)**: Rust 기반의 WebAssembly(WASM)와 `lol-html` 스트리밍 파서를 결합하여 [cite: 5][cite_start], 유저 응답 과정 중 메모리 적체 없이 바이트 스트림 단위로 노이즈 제거 및 기본 'Skeleton JSON-LD'를 주입하여 50ms 미만의 TTFB 최적화를 보장합니다[cite: 17, 24, 31, 32].
* [cite_start]**Cold Path (오프라인 처리 영역)**: 실시간 레이턴시 제약에서 벗어나 고비용의 LLM 연산, 시맨틱 분석, 지식 그래프 빌드를 비동기적으로 처리하여 데이터의 질적 고도화에 집중합니다[cite: 78, 79, 80]. 리소스 오버헤드를 완벽히 차단하기 위해, 큐를 감시하며 작업을 직접 인계받는 **상주형 워커(Resident Worker) 기반의 비동기 Pull 매커니즘**을 탑재합니다.

### 1.2 시스템 구성 요소 및 상세 역할
* [cite_start]**Akamai EdgeWorkers (Traffic Router)**: 트래픽의 최전방 진입점으로서 요청 URL을 판별해 GEO 최적화 대상인 경우 본문을 읽지 않고 헤더와 URL 정보만 Akamai Function(Spin) 엔드포인트로 고속 Forwarding합니다[cite: 7, 8, 10, 11].
* [cite_start]**Akamai Function (Streaming GEO Engine)**: Reverse Proxy로서 Origin 서버의 HTML 바이트 스트림을 수신하는 동시에 `lol-html`로 실시간 스트리밍 리라이팅을 수행합니다[cite: 13, 14, 16, 17]. [cite_start]변환 에러 시 원본 HTML을 즉시 반환하는 Fail-safe 로직을 구동합니다[cite: 19].
* [cite_start]**Edge KV Store (Distributed State)**: 공통 제거 셀렉터 규칙셋이 담긴 `GLOBAL_GEO_RULES`와 오프라인 파이프라인이 발행한 완결형 고품질 데이터를 보관하는 `URL_DATA` 스토어로 구성됩니다[cite: 20, 21, 22].
* [cite_start]**연동 모듈 및 태스크 큐 (Integration & Task Queue)**: 실시간 캐시 미스 시 비동기 큐에 URL 분석 태스크를 밀어 넣는 브릿지 레이어입니다[cite: 357, 358]. [cite_start]분산 환경 내 신뢰성 확보를 위해 Redis 인프라와 분산 락(Distributed Lock) 시스템을 가동합니다[cite: 360, 361].
* **상주형 오프라인 워커 (Resident Cold Path Worker - `main.py`)**: 단발성 프로세스 기동으로 인한 파이썬 인터프리터 스핀업 및 Playwright 브라우저 런타임 초기화 비용을 무력화하기 위해 메모리에 영구 상주하는 비동기 데몬(Daemon)입니다. Redis Queue를 블로킹 팝(`BRPOP`) 형태로 대기하다가 작업을 Pull 방식으로 처리합니다.

### 1.3 중복 방지 및 분산 락(Distributed Lock) 설계 규칙
오프라인 파이프라인 가동 시, 동일 URL에 대한 무분별한 분석 요청 중복 및 큐 적체를 원천 차단하기 위해 Redis 기반의 분산 락 레이어를 연동 모듈 전면에 배치합니다.

* [cite_start]**원자적 제어 확보**: 연동 모듈은 비동기 태스크 큐에 작업을 밀어 넣기 전, 반드시 Redis의 `SETNX` 명령을 가동하여 특정 URL에 대한 제어 권한을 획득해야 합니다[cite: 361, 362]. [cite_start]키 구조는 `Lock:GEO:Analysis:{SHA256(URL)}` 형태로 생성되며 1시간의 유효수명(TTL) 가드타임을 강제 적용합니다[cite: 362, 363]. 이미 해당 키가 존재해 락 획득에 실패하면 추가 인큐 없이 요청을 즉시 드롭(Drop)시켜 멱등성(Idempotency)을 보장합니다.
* **상주형 워커의 안전한 락 해제 메커니즘**: `main.py` 내부의 최적화 파이프라인 처리가 완수되거나 에러로 인해 종료되는 시점에 반드시 `finally` 블록을 통과하도록 설계합니다. 이때 워커는 Redis의 단일 스레드 특성을 활용한 Lua 스크립트를 호출하여, 현재 락의 가치(Value)가 본인이 가지고 있는 고유 토큰(`worker_token`)과 완벽히 일치할 때만 원자적으로 락을 삭제(`DEL`)하도록 제약합니다. 이를 통해 가드타임 만료로 인해 타 워커가 새로이 생성한 신규 락 소유권을 임의로 오염시키는 리스크를 무결하게 방어합니다.

### 1.4 3-Tier 검증 및 Fail-safe 가드레일
[cite_start]LLM 분석 결과물이 지닌 구조적 결함이나 할루시네이션(Hallucination)이 실서비스 에지 환경을 오염시키는 것을 차단하기 위해 최종 배포 전 단계에 삼중 가드레일을 연결합니다[cite: 155, 331].

* [cite_start]**[Tier 1] 구문 및 규격 검증 (Syntactic Validation)**: LLM이 반환한 JSON 데이터가 파싱 가능한 형태인지 심사하고, JSON Schema Validator를 통해 필수 필드가 규격을 엄격히 준수하고 있는지 검증합니다[cite: 222, 332, 335]. [cite_start]문법적 미세 결함 발생 시 정규표현식 자동 보정 또는 재요청을 수행합니다[cite: 336].
* [cite_start]**[Tier 2] 구조적 정합성 검증 (Structural Alignment)**: 제안된 HTML 보정안(`structural_audit`) 내 기술된 CSS Selector 구조가 실제 정제된 HTML 내에 존재하는지 `lol-html` 엔진으로 매칭 테스트하여 마크다운 계층 정합성을 사전에 확인합니다[cite: 337, 338, 340].
* [cite_start]**[Tier 3] 의미론적 진실성 검증 (Semantic Truth Check)**: 지어낸 거짓 정보 유입을 필터링하기 위해, 생성된 JSON-LD 내부의 핵심 엔티티 속성이 최초 수집된 원본 클린 HTML 텍스트 내에 실제로 실재하는지 교차 문자열 매칭(Text Grounding)을 수행합니다[cite: 155, 342, 343, 345].
* [cite_start]**보정 및 단계적 강등 (Graceful Degradation)**: 검증 단계에서 치명적 불합격 판정을 받거나 인프라 통신 오류 발생 시, 오프라인 정밀 데이터 업데이트를 무효화하고 실시간 스트리밍 엔진이 생성한 기본 안정형 'Skeleton' 메타데이터 구조를 그대로 유저에게 제공함으로써 에지 환경 특유의 고가용성과 리소스 연속성을 보장합니다[cite: 347, 351, 352].

## 2. Redis 인프라 구축 및 최적화 설정
